# Application workflow milestone

## What this adds

- Student web and mobile application submission.
- Private resume uploads to the `resumes` Supabase Storage bucket (PDF/DOC/DOCX, maximum 10 MB).
- Duplicate application prevention through the unique `(job_id, applicant_id)` constraint.
- Student application tracking with live Supabase Realtime updates.
- Recruiter application queue, status changes, and 60-second signed resume URLs.
- In-app notifications generated by database triggers for new applications and status changes.

## Apply migrations in order

Run both SQL files in the Supabase SQL Editor, in filename order:

1. `supabase/migrations/202611090001_initial_schema.sql`
2. `supabase/migrations/202611090002_application_workflow.sql`

The second migration narrows application updates to the `status` column, validates status transitions in a trigger, prevents applicants from submitting another user's ID or a resume path outside their own UUID folder, and makes notification writes trigger-owned.

## Routes

- Web job application: `/jobs/[jobId]/apply`
- Student application tracking: `/student/applications`
- Recruiter application management: `/recruiter/applications`
- In-app notifications: `/notifications`
- Mobile: Explore tab's Apply action and Applied tab

## Storage and authorization

The `resumes` bucket is private. Client code uploads to `<auth.uid()>/<random-id>-<filename>`. A recruiter cannot list the bucket or read arbitrary files; Storage RLS permits reads only when the path is attached to an application for a job managed by that recruiter. Recruiter UI requests a 60-second signed URL only after the signed-in client is authorized by Storage RLS.

The web and mobile apps use only the Supabase publishable key. Never add a service-role key to a browser or mobile environment file.

## Manual acceptance test

1. Sign up as a student and complete email confirmation if enabled.
2. Sign up as a recruiter, create a company, publish a job.
3. Sign in as the student in web or mobile and apply with a test PDF under 10 MB.
4. Confirm a row appears in `public.applications`, the resume object exists in the private bucket, and the recruiter receives a new-application notification.
5. Sign in as the recruiter and open `/recruiter/applications`; confirm only managed-company applicants appear and the resume opens via a signed URL.
6. Move the application from `submitted` to `reviewing`, then `shortlisted` or `rejected`.
7. Confirm the student's web `/student/applications` and mobile Applied tab update without manual refresh, and `/notifications` receives the status notification.
8. Try a duplicate application, a file larger than 10 MB, a disallowed file type, a forged applicant ID, a forged resume path, and an unauthorized status change. All must fail.

## Remaining before production

- Run the full app build/type checks after installing dependencies in the developer environment.
- Validate Storage MIME/size rules with real uploads; MIME types alone do not scan file contents. Add malware scanning and consider signed URL audit logging for production.
- Add rate limiting / CAPTCHA to public signup and application submission.
- Configure Resend for transactional email; in-app notifications do not send email.
- Configure Expo push tokens and a trusted server/Edge Function for push delivery; Realtime is currently used for in-app foreground updates.
